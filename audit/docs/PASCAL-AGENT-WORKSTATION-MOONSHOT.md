## What Gemma buys, and how to test fit

Gemma 4 E2B/E4B are dense with per-layer embeddings (PLE), as is the 12B Unified in the sense of not being MoE. The 26B-A4B is the actual routed MoE, about 3.8B active, with 14.4 GB (~13.4 GiB) official text QAT weights. This exceeds the two larger cards' 13 GiB before placement, cache, work areas, or headroom. Three cards have 15 GiB nominal, not a single pool, and using all three sacrifices the resident roles. An earlier author-run GTX 1080 hybrid experiment recorded roughly 20 tok/s no MTP and 24.5 tok/s with MTP, but with CPU experts, a different fork/quant/placement, and a short actual input despite large context allocation. This is proof of feasibility, not a Z4 projection. Google reports LiveCodeBench v6 of 77.1% (26B), 72.0% (12B), 52.0% (E4B) and 44.0% (E2B). These are the publisher's quality results, not matched quantized tool-loop measurements. [Google model card](https://gemma.ai/models/gemma-4/model-card/), [26B weight file](https://huggingface.co/google/gemma-4-26B-A4B-it-qat-q4_0-gguf/tree/main), [GTX 1080 run logs](https://dev.to/mdda/running-gemma-4-26b-on-an-old-gtx-1080-with-llamacpp-4fi5), [PLE implementation notes](https://gemma.ai/tuning/best-practices/). One [E4B host-mapped report](https://github.com/ollama/ollama/issues/19357) saw roughly 3.1 GiB VRAM at 16K, on a different artifact/runtime. Use it as a placement lead, not a fit guarantee.

Separate heavy mode: first try Liquid's 24B-A2B QAD-Q2_K_L (9.54 GB, ~8.89 GiB) split by contiguous layers across P104/P2000; P620 stays dispatcher. This is a trained low-bit checkpoint, not a guarantee of quality. Compare to resident LFM8B and the existing dense baseline on the same completed tasks; keep as optional only if it adds a capability the M6000 complement does not already cover better. Gemma26 is the next probe only with a real per-device budget (an approved smaller artifact or measured warm host expert cache). Official QAT, single-GPU CPU-offload and capacity-max 3-way are separate arms, not interchangeable. Do not buy RAM, make swap a solution, silently alter context, or move hardware. [Official LFM24B files](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B-GGUF/tree/main), [upstream split modes](https://github.com/ggml-org/llama.cpp/blob/master/docs/multi-gpu.md).

## Fund three rewrites; do not spend the night on isolated 2% patches

1. **Session runtime: preserve state across tool turns and overlap independent work.** Freeze a native template per role and keep immutable system/tool prefixes where template semantics allow. Key checkpoints by model/quant, token prefix, runtime/cache format and session boundary; persist attention KV plus hybrid convolution/recurrent state (and matching position metadata), not just the transcript. Restore from the longest valid checkpoint on template rewrite; fail closed to re-prefill on divergence. A/B against the same native template with stock warm slot behavior and then pinned-prefix/reference replay. Separate changes in prompt bytes from same-prompt backend savings. Feed compact, schema-validated worker/evidence results; prove that replacing large repeated tool payloads does not lose facts required downstream. Let independent retrieval/summarization run concurrently with P104 work, but do not parallelize steps that depend on each other's output. Stretch: 1.5–2x throughput of successful jobs or equivalent median latency improvement on the actual trace, with unchanged success; e.g. if 60% of elapsed time is repeated work and 80% of that portion disappears, the ceiling from that change is 1/(1−0.60×0.80) ≈ 1.92x. Measure the two fractions before implementing storage architecture. [Upstream cache-reuse failure case for hybrid Qwen](https://github.com/ggml-org/llama.cpp/issues/32316).
2. **CUDA decode: short-row DP4A target verify, not a new generic matvec.** Start with a stock Gemma E4B or 12B matched official assistant on the same device if it fits; compare draft 1/2/4 to serial. Prototype one specialization for the actual dominant path: keep activations quantized across dependent projections or fuse short-row routed gate/up/down scheduling and deterministic reduction, using n=1/2/4/8 measured on sm_61. For Gemma use the native paired assistant and shared KV; do not use a random different Gemma as a drafter. For Qwen use its own compatible baseline/assistant only in a separate lane. P620 drafter is an optional later topology experiment, only after measured shared-state placement, device synchronization and PCIe costs. Acceptance alone is not the gate: compare wall time per emitted token (verification + draft + sync divided by actual emitted tokens), greedy tokens and tool-call outcomes. Keep a draft-disabled arm and per-dispatch proof. Target at least 1.25x verified decode and a visible task win to justify ongoing maintenance. [Gemma paired assistant](https://gemma.ai/get-started/capabilities/mtp/), [upstream MTP](https://github.com/ggml-org/llama.cpp/pull/23398), [reported CUDA reduction/verification interaction](https://github.com/ggml-org/llama.cpp/issues/29168).
3. **MoE residency and few-row executor: stop treating experts like layers.** First test fully resident LFM8B versus Qwen9B and inspect actual router, expert traffic and recurrent/attention work at n=1 and n=2–8. For LFM24B/Gemma26 capacity mode, compare ordinary layer split against upstream host expert cache *before* rewriting it. Record real per-layer expert IDs, bytes, churn, miss timing, overlap, and effective link bandwidth; use distinct train/holdout task traces for replay. If a trace-driven shadow cache plus measured transfer/compute costs predicts at least 1.30x over the best feasible baseline, prototype one split-residency scheduler: contiguous layer ownership, local hot expert slots, grouped small-row dispatch, overlapped pinned miss transfers (or measured cheaper CPU compute), and zero change to top-k/expert set. Do not pull whole expert matrices across PCIe per token, assume P2P, or require resident roles to compete for the same card. If hit rate or bytes per token do not support it, stop the cache rewrite and spend the branch on a real routed dispatch/fusion or stay fully resident. [Upstream expert cache](https://github.com/ggml-org/llama.cpp/blob/master/docs/moe-cache.md), [routed layout baseline](https://github.com/ggml-org/llama.cpp/pull/31047). Treat targets as screening thresholds, not expected gains.
