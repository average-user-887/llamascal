# CARD-5 Pascal quantised-KV flash attention: GQA-packed VEC kernel for q8_0/q4_0 at 1..4 query tokens (decode + MTP verify) -> long context in 8 GB
Question: On cc 6.1, q8_0/q4_0 KV decode goes to the VEC kernel with one block per Q head (fattn-vec.cuh:108-113), so each K/V row is read gqa=4 times. MTP verify (3 tokens) and prefill go to TILE, which first dequantises the whole cache to an f16 temp buffer (fattn-common.cuh:1087-1130, fattn.cu:768-781). Can a GQA-packed native-quant kernel make q8_0 KV as fast as f16, so 96k-128k context fits?
Hypothesis: KV per token: f16 32 KiB, q8_0 17 KiB, q4_0 9 KiB (8 attn layers x 4 kv heads x 256 x K+V). VRAM for KV in serving ~2.1 GiB -> f16 ~68k, q8_0 ~126k, q4_0 ~240k tokens. Today q8_0 tg at 16k = 32.2 vs f16 35.2 (-8.4%) [M queue fa-kv-matrix], consistent with 4x K/V reads. Packing the 4 Q heads of a KV head into one block (ncols2 = 4, Q in registers/smem, K dot via dp4a on q8_0/q4_0 with Q quantised to q8_1 once per block) reads K/V once: q8_0 at 16k ~ f16 parity (+8%), at 64k+ q8_0 beats f16 (half the bytes). For n_tokens 2..4 (verify), the same kernel with ncols1 = n avoids the TILE dequant at long context. f16 path: TILE gqa_opt at d8192 runs at ~1.8x the bandwidth bound (1.57 vs 0.88 ms); a packed VEC f16 variant may take ~0.5 ms/token at 8k (+2%).
Phase B (not tonight unless phase A is done by 01:00): TILE kernel loading q8_0/q4_0 tiles into shared memory and converting there (no global f16 temp) for prefill at 128k: at 128k the temp buffer would be ~1 GiB and not fit.
